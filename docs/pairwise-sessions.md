# MeshLake 成对加密会话

## 目标

早期数据面直接使用每个虚拟网络共享的一把流量密钥。它可以阻止中继读取载荷，却不能阻止已经加入网络的恶意成员伪造其他 DeviceId 的数据帧。

当前数据面改为每对设备独立的临时会话：

```text
控制器签名成员证书
        │
        └──> Ed25519 设备身份认证
                    │
                    └──> 临时 X25519 握手
                              │
网络 PSK ──> HKDF-SHA256 ─────┤
                              ├──> A 到 B 会话密钥
                              └──> B 到 A 会话密钥
```

## 握手

1. 发起方生成随机 128 位会话 ID 和一次性 X25519 密钥对。
2. 发起方使用长期 Ed25519 设备私钥签名网络 ID、双方 DeviceId、会话 ID、临时公钥和时间戳。
3. 接收方从控制器签名成员证书取得发起方 Ed25519 公钥，验证签名、身份、网络和 120 秒时钟窗口。
4. 接收方生成自己的临时 X25519 密钥对，并签名包含双方临时公钥的响应。
5. 双方计算 X25519 共享秘密，再用 HKDF-SHA256 混合网络 PSK、双方身份、双方临时公钥和会话 ID，输出两个方向各自独立的 256 位密钥。

临时 X25519 私钥不会写入状态文件。仅获得网络 PSK、长期身份公钥或抓取握手报文，均不足以恢复会话密钥。

双方同时发起握手时，DeviceId 较小的一方保持发起方角色，使双方收敛到同一个会话。握手包每秒重试，10 秒仍未完成则丢弃；等待期间每个对端最多缓存 8 个 IP 包。接收端对已经验证的会话 ID 保留 5 分钟记录：当前会话的重复请求只重发原响应，旧会话的重放不能替换当前密钥。

## 数据帧与防重放

每个 `RELAY_SESSION_DATA` 帧包含：

- 网络 ID；
- 源和目标 DeviceId；
- 128 位会话 ID；
- 64 位单调包序号；
- XChaCha20-Poly1305 密文与认证标签。

XChaCha20 nonce 由会话 ID 和包序号唯一构造。以上全部外层字段都作为 AEAD 附加认证数据，因此中继无法在不被发现的情况下修改路由或序号。

接收方在认证成功后才更新 64 包滑动窗口：重复包、窗口之外的旧包以及认证失败的包均不会进入 Wintun/TUN。认证失败的超前序号也不会推动窗口，避免攻击者用伪造包阻断合法流量。

会话最长使用 1 小时；过期后，下一批业务数据触发新的临时握手。包序号接近耗尽时也会强制重新握手。

## 直连与中继

握手、响应和会话数据都可以走同一个已发现的直连 UDP 路径，也可以由 `meshlake-relay` 按目标 DeviceId 转发。中继不解析签名载荷，不持有网络 PSK、设备私钥或会话密钥。

有效的成对加密数据可以证明发送端持有当前会话密钥。只有在成功认证数据帧后，客户端才会把新的直接来源端点加入可用候选，避免仅凭可重放的握手报文劫持路径。

## 升级与安全边界

- 新客户端只接受成对会话数据，不接受旧的共享网络密钥 `RELAY_DATA` 帧。
- 根节点目录必须携带完整的控制器签名成员证书；旧根节点只有地址和候选时不能建立会话。
- 新中继需要转发三种会话帧，但仍可盲转发旧帧以便分阶段替换；安全边界由接收客户端决定。
- 当前状态文件尚未接入 Windows DPAPI、TPM 或 Linux Secret Service。磁盘上的设备身份私钥和网络 PSK 必须由操作系统权限保护。
- 对端证书必须出现在本网络当前控制器签名授权清单中；成员删除或授权过期会清除传输线程中的旧目录和成对会话。正常刷新约为 20 秒级，拒绝配合客户端的最坏窗口由 90 秒授权租约限定。
