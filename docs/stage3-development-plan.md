# 阶段 3：生产化验收与运维安全

阶段 3 从 `main@b3d3bd1` 开始。阶段 2 已完成安全状态备份、签名 DNS/自定义路由、会话可观测和离线系统测试计划；本阶段不继续横向堆叠功能，而是把现有无 GUI 核心推进到可安全部署、可重复验收、可诊断的状态。

## 总目标

1. 从进程参数、shell 历史和非交互日志中移除管理员令牌、入网令牌与完整邀请链接。
2. 将 `tests/system` 从离线计划器扩展为带强制安全护栏的执行器。
3. 在用户明确授权的隔离测试环境中完成 Windows/Linux 跨主机验收。
4. 加固 Root/Relay 身份、健康确认和授权 epoch 收敛，缩短故障与吊销的不确定窗口。
5. 形成可重复的 Windows 服务与 Linux systemd 安装、升级、回滚和状态权限流程。
6. 为 Linux 无界面服务建立明确的静态秘密保护方案，避免把桌面 Secret Service 当作 root/systemd 服务的唯一依赖。

## 不属于阶段 3

- 不实现 `0.0.0.0/0`、`::/0` 或出口节点。
- 不自动开启主机 IP forwarding、防火墙放行或 NAT。
- 不接入真实用户服务器、虚拟机或云资源，除非用户另外提供明确授权、主机清单和允许执行的动作。
- 不把 GUI、移动客户端、TURN 数据面或大规模集中式管理作为阶段 3 的合并阻塞项。
- 不改变成员证书、钉扎控制器、成对会话、重放窗口、网络密钥 epoch 和 Planet 隔离边界，除非有独立协议版本、迁移方案和兼容性测试。

## 并行开发任务

### A. 安全运维入口

建议分支：`codex/stage3-secure-operations`

- 为 `--admin-token`、`--token` 和 `network join-link --link` 增加隐藏交互、标准输入或受限文件输入。
- 同一秘密只能选择一种输入来源；默认错误和日志不得回显秘密、完整链接或其可恢复片段。
- 控制器首次初始化不得在非交互式 stderr 中直接输出管理员令牌。支持显式受限文件或交互式领取，并原子创建文件。
- Linux 秘密文件必须拒绝宽松权限；Windows 使用受限 ACL，并验证服务身份能够读取、普通用户不能继承意外权限。
- 为 Linux 状态信封定义可插拔主密钥来源：优先评估 systemd credentials/TPM2 sealed key，交互式用户场景可选 Secret Service；保留 `0600` 兼容模式时必须显式报告安全等级，禁止配置错误后静默降级。
- Linux 新旧状态格式必须版本化迁移，并继续兼容阶段 2 的口令保护跨机器备份；TPM 绑定状态不能直接复制到其他主机冒充可恢复备份。
- 为 Windows Service 和 Linux systemd 明确状态目录、服务账户、停止后备份/恢复、升级和回滚流程。
- 加入参数解析、日志脱敏、文件权限、并发锁、迁移和异常退出测试。

验收门槛：真实秘密不再需要出现在 argv；首次初始化可以在无人值守服务场景安全完成；Linux 保护模式不会静默降级；现有命令兼容期有明确弃用提示和移除计划。

### B. 可执行系统测试框架

建议分支：`codex/stage3-system-test-executor`

- 保持当前默认行为为纯计划和校验；只有显式 `--execute` 才允许执行动作。
- 首先实现本地进程和容器执行后端，再实现 SSH/WinRM 适配器；远程后端不得在普通 CI 中自动启用。
- inventory 只保存主机角色和非秘密连接引用；密码、令牌、私钥、PSK 和邀请链接必须来自进程外秘密源。
- 每个破坏性动作同时要求场景声明、允许列表和一次性 `lab_id` 确认；目标必须是明确标记的可丢弃测试主机。
- 每个动作提供超时、幂等清理和失败回滚；运行结束必须恢复路由、DNS、适配器与临时服务。
- 采集结构化、脱敏的日志与 `/v1/sessions` 快照，不采集数据包内容、端点秘密或密钥材料。
- 实现现有五个场景，并新增路由/DNS 部分失败、回滚失败、适配器关闭、备份恢复和控制器 TLS 场景。

验收门槛：无 `--execute` 时零副作用；错误目标、缺少确认、秘密写入 inventory 或清理步骤缺失时必须失败关闭。

### C. Root/Relay 与授权收敛加固

建议分支：`codex/stage3-root-relay-hardening`

- 为 Relay 注册确认增加可验证的服务身份签名，绑定网络、设备、Relay 身份、请求 nonce、端点和短时有效期，替代仅依赖源地址与随机 nonce 的健康确认。
- 明确 Root/Relay 身份轮换、Planet 双签过渡和旧身份撤销流程。
- 设计控制器签名的最新授权 epoch 提示或拉取机制；它只能促使节点获取并验证新清单，不能代替完整签名授权清单或延长过期时间。
- 为多 Root/Relay 的失败、恢复、乱序响应、旧 epoch、重放、时钟偏差和服务重启增加确定性测试。
- 对健康探测和重新注册加入退避与抖动，避免故障恢复时形成请求尖峰。
- 补充不含敏感材料的健康与收敛指标，纳入会话可观测输出或独立版本化 API。

验收门槛：伪造、重放、跨 Relay 和旧身份确认不能把 Relay 标记为健康；吊销安全仍以控制器签名清单和既有限时 fail-closed 规则为最终边界。

## 主线合并顺序

1. **安全运维入口**：先消除后续自动化必然接触的 argv 与日志秘密风险。
2. **可执行系统测试框架**：再建立可审计、默认无副作用的验收工具。
3. **Root/Relay 与授权收敛加固**：最后使用执行器覆盖新的协议和故障行为。

主线统一负责公共接口审查、冲突处理、README/阶段文档、`Cargo.lock`、最终测试和 CI。每个分支只提交自身范围，不连接用户基础设施、不修改 GUI，也不自行合并或推送 `main`。

## 授权后的跨主机验收矩阵

只有在用户明确授权后，才为指定的可丢弃主机生成实际 inventory 并执行：

| 维度 | 最低覆盖 |
| --- | --- |
| 主机组合 | Windows↔Windows、Linux↔Linux、Windows↔Linux |
| 地址族 | IPv4、IPv6、双栈 |
| 数据路径 | 直连、直连失败转 Relay、首选 Relay 故障切换 |
| 控制面 | Root 故障恢复、控制器 TLS、授权刷新、成员吊销 |
| 生命周期 | daemon 重启、服务升级回滚、状态备份跨机恢复 |
| 网络策略 | 路由/DNS 应用、部分失败、回滚失败后适配器关闭 |

验收产物只能包含提交哈希、平台版本、场景结果、耗时、脱敏日志和计数器。真实地址、账户、口令、令牌、邀请链接、私钥和网络 PSK 不得进入仓库或 CI artifact。

## 阶段 3 完成标准

- 三个开发任务均经主线安全审查和定向测试后合并。
- `cargo fmt --all -- --check`、`cargo check --workspace --locked`、`cargo test --workspace --locked`、`cargo build --workspace --release --locked` 全部通过。
- Windows/Linux CI 的测试、release 构建、打包和 artifact 上传通过。
- 敏感信息扫描、依赖审计、`git diff --check` 和系统场景离线校验通过。
- 执行器的安全护栏有单元测试；未经授权的 CI 或开发机不会连接外部主机。
- 获得测试环境授权后，完成上述跨主机矩阵；若尚未授权，代码可以合并，但阶段 3 只能标记为“实现完成，真实环境验收待授权”。

## 后续阶段

- **阶段 4：出口与受限网络能力**——单独设计出口节点授权、默认路由、DNS 泄漏保护、kill switch、管理员显式启用的 IP forwarding/NAT，以及 TURN/TCP/TLS 受限网络回退。
- **阶段 5：终端产品化**——在无 GUI 核心稳定后，再推进移动客户端、桌面 GUI 完整管理、安装器、自动更新和长期兼容策略。
